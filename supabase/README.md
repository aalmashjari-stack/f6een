# مخطّط قاعدة البيانات

ملفّات الهجرة في `migrations/` — تُقرأ بالترتيب الزمني لأسمائها. مصدرها
`docs/SPEC.md` القسمان ٨ و٩، لا تصميمٌ مستقلّ.

| الملف | ماذا يبني |
|---|---|
| `…_profiles.sql` | صفُّ حساب لكل مستخدم، وفيه `games_balance` — الجديد يبدأ بجلستين |
| `…_used_questions.sql` | ذاكرة الأسئلة الدائمة، و«الأقدم استخداماً» عند نفاد المستوى |
| `…_sessions.sql` | الجلسة ونافذة الاستكمال، ودالّة `start_session` التي تخصم |
| `…_gift_codes.sql` | أكواد الهدية، واستخدام واحد لكل حساب مفروضٌ في المفتاح |

## القاعدة الحاكمة

**لا يكتب العميل رصيداً ولا يُنشئ جلسة.** الجداول التي تمسّ المال مقفولة
بـRLS على القراءة فقط، والتغيير يمرّ حصراً بدالّتين `security definer`:

- `start_session(initial_state jsonb)` — تُرجع الجلسة المفتوحة إن وُجدت
  (استئناف بلا خصم)، وإلّا تخصم لعبة وتُنشئ واحدة. الخصم والإنشاء في معاملة
  واحدة، وشرط الرصيد داخل `update` نفسه فلا تتسلّل طلبتان متزامنتان.
- `redeem_gift_code(p_code text)` — تتحقّق من الانتهاء والسقف، وتقفل صفّ
  الكود بـ`for update` فلا يتجاوز استبدالان متزامنان السقف.

بدون هذا، أيّ لاعب يفتح أدوات المطوّر ويكتب `games_balance = 999` عبر
`supabase-js` مباشرةً.

## التطبيق

في لوحة Supabase ← **SQL Editor**، الصق محتوى كل ملفّ بالترتيب واضغط Run.
أو بالـCLI:

```bash
npx supabase link --project-ref <ref> && npx supabase db push
```

## غير مبنيّ بعد

- **المصادقة** — لا مزوّد محسوم. الجداول تشير إلى `auth.users` فتعمل مع أيّ
  مزوّد يُفعَّل لاحقاً بلا تعديل.
- **الشراء** — `games_balance` يزيد اليوم عبر كود الهدية وحده. مسار الدفع
  «غير محسوم» في SPEC القسم ١٣.
- **نطاق ذاكرة الأسئلة** — SPEC ١٣ يسجّل أنّ الحساب يمثّل المضيف لا المجموعة،
  والاقتراح فيه سجلّ منفصل لكل مجموعة. المخطّط الحالي يتبع القرار القائم:
  سجلّ واحد لكل حساب.

## لوحة الإدارة

الصفحة `admin.html` (على الويب: `f6een.com/admin.html`) تقرأ الحسابات
والجلسات والأكواد والبلاغات، وتعدّل الرصيد وتنشئ الأكواد وتحذفها.

**الصلاحية صفٌّ في `public.admins` لا دورٌ في رمز الدخول.** الرمز يحمل ما
يكتبه العميل، وجدولُ الإدارة بلا سياسة قراءة ولا كتابة — لا يُضاف إليه إلّا
من محرّر SQL. وكل دالّة إدارة تشترط `is_admin()`: من ليس مديراً يرى صفر
صفوف أو `not_admin`، ولو فتح الصفحة بنفسه. **فإخفاء العنوان ليس حراسة،
والحراسة لا تحتاج إخفاءً.**

### الترتيب — كل دالّة في تشغيل مستقلّ

| # | الملف | ماذا يبني |
|---|---|---|
| ١ | `…_admins.sql` | جدول المديرين، بلا سياسات |
| ٢ | `…_is_admin.sql` | الحارس `is_admin()` |
| ٣ | `…_admin_read_policies.sql` | قراءة الجداول الخمسة للمدير |
| ٤ | `…_admin_users.sql` | كل الحسابات ببريدها من `auth.users` |
| ٥ | `…_admin_set_balance.sql` | تعديل رصيد حساب |
| ٦ | `…_admin_sessions.sql` | الجلسات كلّها |
| ٧ | `…_admin_gift_codes.sql` | الأكواد وحصيلة كلٍّ منها |
| ٨ | `…_admin_create_gift_code.sql` | إنشاء كود |
| ٩ | `…_admin_delete_gift_code.sql` | حذف كود |
| ١٠ | `…_admin_reports.sql` | بلاغات الأسئلة من حالات الجلسات |
| ١١ | `…_admin_stats.sql` | الأرقام الجملية |

**تُلصق ملفّاً ملفّاً في تشغيلات منفصلة**، لا الكلّ دفعةً واحدة: محرّر SQL
يبتلع أجساد `$$ … $$` حين تُلصق مع غيرها فتُنشأ الجداول وحدها ويقول
«Success» — وقع مرّتين قبل هذه اللوحة. وبعد كل دالّة يُتحقّق بندائها لا
بغياب الخطأ.

### تعيين أوّل مدير

بعد الملفّات الأحد عشر، في محرّر SQL:

```sql
insert into public.admins (id, note)
select id, 'المالك' from auth.users where email = 'ALI@EXAMPLE.COM'
on conflict (id) do nothing;
```

ثمّ افتح `/admin.html` بنفس الحساب. لا واجهة تضيف مديراً — عمداً.
